# Implementation contract

This contract freezes issues #4–#10 before implementation. It applies to native plugin-compatible routes only; standalone skill/command distribution is excluded. Pi and OpenCode retain reader/remover support only to clean up old plgnz-owned installations. Gemini CLI may remain a native-extension candidate, but that surface is unverified and is not treated as standalone.

## Sources and identity

`add <source>` accepts an explicit local plugin root or collection, or an explicit Git source. `--plugin <name>` is repeatable and selects named packages from a collection before target activation. A local source is materialized from its supplied bytes. In particular, a Personal bundle is authoritative: plgnz must not fetch, replace, or normalize away its amended vendor bytes or provenance. Remote fetch occurs only for a remote input.

Discovery returns one or more `PluginSource` values with `dir`, `name`, optional `version`, optional `marketplace`, and optional `contentFingerprint`; `ResolvedSource` carries normalized `sourceUri`, `sha`, `isGit`, and `plugins`. A collection with zero packages is a required failure. Duplicate package/native identities, unknown requested plugins, unknown or absent requested targets, and unknown CLI flags are required failures before active writes. Selection does not change the source marketplace identity; each resulting install record retains the selected package's native identity.

## Outcome and CLI

Mutation `--json` writes only the schema-v1 `LifecycleReport` envelope to stdout; progress and human logs use stderr. The public types, enum values, stable reason codes, and validator live in `src/lifecycle-report.ts`. The envelope contains command/dry-run/source-snapshot context, an ordered frozen plan, an ordered outcome for every planned operation, and an aggregate summary. Plan action, operation result, resource state, activation state, route, changed flag, and coverage (`desired-pair` or `retirement`) remain separate fields.

Operation result answers whether the Desired operation converged, not whether a protective containment step ran. `retain-prior` and `disable-nonconforming` therefore remain failed pair outcomes with their exact structured reason; resource, activation, and changed fields separately show the retained prior activation or successful reversible disablement. This preserves pair-local diagnostics and prevents containment from serializing as a successful install.

Every pair plan and outcome row carries the canonical nested `DeploymentScopeIdentity` (Source binding plus target kind and instance), along with source-snapshot, package, and native identity. Command-global failures that occur before a pair can be identified live only in the summary; the report never invents a wildcard or nullable pair scope. The validator rejects missing, duplicate, unexpected, out-of-plan, or identity-contradicting outcomes. Structured reasons keep category, stable code, diagnostic, and nullable capability/evidence identifiers; unknown exceptions are internal defects rather than capability gaps. Exit `0` means converged, exit `1` means a valid request did not converge, and exit `2` means usage or selection error.

A valid dry run returns the planned terminal state with `command.dryRun: true`, `changed: false`, and no mutation. Multi-target runs may mix outcomes and exit nonzero if any required target fails. `--legacy-json` explicitly serializes the former `InstallOutcome[]` shape for one transition release only; legacy types stay in `src/legacy-install-outcome.ts` and are not an execution model. Read verbs (`list`, `doctor`) retain their existing host-native JSON shapes and accept repeated `--target` filters. `doctor` stays reader-only. A profile gates only the semantics it cannot evidence: it must not label an entire requested host `unverified` when the requested operation is supported.

`plgnz --version --json` emits `{ "name": "plgnz", "version": <package version> }` so callers can verify the pinned CLI before mutation.

## Records, staging, and refresh

Each owned installation record preserves its existing `host`, `id`, `source`, `sourceSha`, `installedAt`, and optional sorted `pins` fields. Additive optional `fingerprint` and `ownership` fields support content refresh and owned cleanup. `ownership` identifies only plgnz-created representations eligible for replacement or removal. A `pending: 'install' | 'remove'` intent is atomically persisted before its host mutation and cleared only after successful activation and ledger finalization. Interrupted work remains visible in `list` and `doctor` and is retried through the same mutation verb; no recovery daemon or global transaction is implied.

New records also retain the selected canonical `sourceDir` and an `installedFingerprint` captured from the activated host-native content. An `InstalledPlugin` may declare optional nonempty `contentRoots`: labeled absolute roots whose sorted, framed tree fingerprints form that installation proof; without them, the native `path` tree fingerprint remains byte-identical to the legacy proof. `path` remains the host's display and native identity. Doctor recomputes the source tree fingerprint and the native installation fingerprint independently. It reports fresh only when the native install is present and enabled, neither proof changed, and no mutation is pending. Legacy records without complete byte proof are unverified; missing, changed, unreadable, or symlinked source/native content is stale. This byte proof is independent of the source-revision freshness check: a matching Git head alone never proves installed content.

Adapters stage converted content, validate the staged representation, then activate it. A conversion/validation failure retains the active owned representation. Re-add is `unchanged` only when the selected source, target representation, and content fingerprint match. Changed local bytes refresh even when version and source revision do not. `update` reuses the record's source/selection, refreshes only owned artifacts, and reapplies recorded pins. `remove` refuses unrecorded artifacts.

Codex cache slots carry a `.plgnz-install.json` marker with their source identity, plugin id, and fingerprint. An explicit add may mark an unowned slot without `--adopt-existing` only when every staged byte already matches. Replacing a differing unowned slot requires `--adopt-existing`, a matching cached manifest name/version, and no foreign version that would remain active. Malformed markers and markers for another source are always refused. Cleanup failure after activation leaves the new active slot and pending ledger intent intact; it never deletes the new slot in an attempted rollback.

## Profiles and conversion

`src/semantic-inventory.ts` inventories immutable Source bytes before host preparation. It types ordinary skills, MCP, hooks, commands, agents, independent model- and user-invocation controls, auto-update control, resources, permission/preprocessing semantics, retirement, retention safety, readback, rollback, and activation/reload separately. Every entry in each authored `commands/`, `.claude/commands/`, `agents/`, and `.claude/agents/` root is validated and retained with its root and dialect. Valid roots coexist: their definitions and required semantics form a union, and the same logical identity may have representations in distinct roots. Empty roots, nested or non-file entries, unknown dialects, duplicate identities within one root, and malformed alternate roots are invalid Source input rather than absent components. Command `permissionMode` is permission semantics; the unproven `@{...}` form is invalid preprocessing, while `$ARGUMENTS` and ordinary relative resource references remain ordinary command content. Claude frontmatter aliases and Codex `agents/openai.yaml` declarations remain distinct evidence even when they agree. A malformed boolean/YAML/TOML/JSON declaration or contradictory policy is invalid Source input (`usage.invalid-argument`), never a host capability gap.

`src/capability-evidence.ts` admits a whole package against an evidence profile keyed by host, exact detected version, Source type, operation, route, and the operation's complete required-semantic set. Install and update require the complete authored Source inventory before any component activates. Retirement is projected only from recorded lifecycle obligations—retirement, retention safety, exact readback, rollback, and activation/reload—and remains admissible when Source bytes are unavailable; authored runtime components never block cleanup. Profiles and capability reasons expose only content-addressed `sha256:<digest>` evidence IDs; repository paths stay inside the hashed evidence claim. Unknown, unparseable, or unmatched versions are unverified. Diagnostic gaps may list multiple components, but no supported subset is admitted from a refused package.

The pinned dcode 0.1.83 Managed profile admits ordinary skills, MCP, hooks, resources, auto-update control, retirement, retention safety, readback, rollback, and activation/reload. It refuses commands, agents, either non-default invocation direction, and permission/preprocessing semantics independently. The frozen Addy/Vercel/Matt Pocock/Try Skill evidence therefore yields `commands + agents`, `commands`, `model-invocation-control`, and `model-invocation-control` respectively, while an ordinary-only package is eligible and every recorded package remains eligible for safe retirement. No package name appears in route policy.

A `ConsumerProfile` remains the target catalog: scoped surface, observed-or-unverified version, human evidence path, and matching capability-evidence IDs. During the legacy-verb cutover it retains only install/update admission flags; these are not package-semantic evidence and disappear when add/update move to the generic lifecycle core. `src/consumer-profiles.ts` remains intentionally wider than the active native writer registry so old owned Pi/OpenCode installs can still be read and removed safely. CLI and desktop profiles remain distinct. A declared native target without an active adapter returns a per-package `unverified` outcome and performs no host or ledger mutation; a name outside the inventory remains an unknown-target failure. `targets --json` retains its detected-host id array; `targets --all --json` additively emits the complete profile objects, including their scope and capability evidence IDs.

Conversion accepts Markdown/TOML commands and skill directories only when it preserves name, description, explicit-invocation restriction, supported arguments, sibling references, and plugin-owned resources. Relative references may be rewritten only with path containment checks and a tested destination mapping. Executable handlers, permission semantics, and template preprocessing are refused when the target lacks a proven equivalent. Ordinary skills retain automatic discovery. No generic authoring manifest is added.

## First increment and verification record

The first code increment is the bundled Addy → Codex path (nine commands, 25 skills): diagnostics/source, conversion/staging, lifecycle, then native transcript. Each increment starts RED, records the focused command/output and saved action/result, and stays releasable. A native evidence record includes profile/version, source identity/fingerprint, selected target, transcript/readback, elapsed time, and failures. At `0.0.x`, releases are patch-only; no npm publication or fleet rollout is in scope.
